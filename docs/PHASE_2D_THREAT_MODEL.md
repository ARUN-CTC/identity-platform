# Phase 2D Threat Model

Every threat below is assessed against the architecture in `docs/PHASE_2D_ARCHITECTURE.md` and its detail documents. Most of these controls are not implemented yet — this is the threat model the future implementation must satisfy, verified again (as Phase 2C's own stabilization review did) once actually built. **Exception, as of Phase 2D.3 (`docs/PHASE_2D3.md`)**: the `ServiceAccountTenantGrant` control named in threats #19 and #22 below now exists as real, tested code — deny-by-default, database-unique-constrained, full lifecycle (`ACTIVE`/`SUSPENDED`/`REVOKED`, reactivate-only path back from `REVOKED`) — closing the storage/enforcement half of both rows. **Further exception, as of Phase 2D.4 (`docs/PHASE_2D4.md`)**: `POST /oauth/token` now calls that control for real, end to end, for the `client_credentials` grant — see §"Phase 2D.4 implementation status" after the table for which specific threats below are now exercised by live HTTP requests, not merely designed.

| # | Threat | Attack path | Control | Residual risk | Detection | Mitigation |
|---|---|---|---|---|---|---|
| 1 | Authorization code theft | Code intercepted in transit (malicious redirect target, compromised network, browser history/referrer leak) | HTTPS-only redirect URIs; short code lifetime (≤60s); PKCE binds the code to the original requester | An attacker who also captured the `code_verifier` (unlikely — never transmitted except in the final POST) could still exchange it before it expires | Code-exchange volume anomalies; a code presented from an unexpected IP/UA vs. the `/authorize` request | PKCE (ADR-013); exact redirect-URI matching (`docs/OAUTH_ARCHITECTURE.md` §4) |
| 2 | Authorization code replay | A captured, already-exchanged code is presented a second time | Single-use enforcement — atomic consume-on-first-exchange | None if enforcement is correctly atomic | A second exchange attempt of a consumed code is a loud, detectable signal | Treat replay as theft evidence — revoke any token already issued from that code (`docs/OAUTH_ARCHITECTURE.md` §5) |
| 3 | PKCE bypass | A client omits `code_challenge`, or a legacy `plain` challenge method is (mis)implemented | PKCE mandatory for every client, every grant, `S256` only — no `plain`, no omission accepted (OAuth 2.1, ADR-013) | None if the `/authorize`/`/token` implementation actually enforces "mandatory," not "default" | Any `/authorize` request missing `code_challenge`, or specifying `plain`, is itself the detection signal | Reject the request outright rather than silently downgrading security |
| 4 | Redirect URI manipulation | Open-redirect-style parameter smuggling, subdomain takeover, prefix/wildcard exploitation | Exact string match only, no wildcards, HTTPS required except controlled localhost (`docs/OAUTH_ARCHITECTURE.md` §4) | A registered redirect URI's own domain being compromised (outside this platform's control) | Registration-time review; anomalous redirect-URI-mismatch rejection rate | Per-environment distinct `Application`s (no redirect URI spans environments) |
| 5 | Client secret leakage | Secret committed to source control, logged, or exfiltrated from a compromised deployment | Hash-only storage (never recoverable even by this platform); one-time display at creation/rotation; overlap-window rotation | A leaked secret is fully usable until rotated/revoked | Anomalous client_credentials usage volume/origin; Platform Operator-visible audit trail of every token issuance per client | Immediate revocation (`secretRevokedAt`, no grace period) distinct from routine rotation's overlap window (`docs/APPLICATION_AUTHORIZATION.md` §6) |
| 6 | JWT forgery | An attacker without the private key attempts to mint a valid-looking token | Asymmetric signing (RS256) — forgery requires the private key, which never leaves the Identity Platform | Only a private-key compromise defeats this — see #9 | Signature verification failure is the detection (every invalid attempt is a hard reject, loggable) | Private key storage discipline (`docs/KEY_MANAGEMENT_ARCHITECTURE.md` §5) |
| 7 | JWT algorithm confusion | A resource server naively accepts `alg: none`, or is tricked into verifying an RS256 token's signature using its OWN public key as an HMAC secret (the classic RS256→HS256 downgrade attack) | Resource servers MUST pin the expected algorithm(s) per `kid`/audience configuration, never accept `alg` from the token header as authoritative on its own, and MUST reject `alg: none` unconditionally | A poorly-implemented third-party resource server ignoring this guidance | Any token with `alg: none`, or an unexpected algorithm for a known `kid`, should be logged and rejected | Explicit guidance + reference validation pipeline (ADR-020) mandates algorithm pinning, not header-trust |
| 8 | `kid` attacks | A malicious/malformed `kid` used to trigger SSRF (a `kid` crafted as a URL some naive libraries fetch) or a SQL/path-injection attempt against a key lookup | JWKS lookup is a simple, bounded, allow-listed `kid`→key map (never a dynamic fetch driven by the token's own `kid` value) | None if the lookup is implemented as a static map/cache refresh, never as "fetch whatever this `kid` says" | Unrecognized `kid` values at volume | `kid` is opaque and validated against the platform's own published JWKS set only — never dereferenced as a URL |
| 9 | JWKS compromise | The JWKS endpoint itself is compromised/tampered (e.g. a CDN/cache-poisoning attack serving attacker-controlled public keys) | HTTPS-only, no intermediary trusted to modify the response; JWKS served directly by the Identity Platform, not a third-party CDN without integrity controls | A sophisticated on-path attacker with valid TLS interception capability (out of this platform's control) | Unexpected `kid`/key changes outside a scheduled rotation window | Scheduled rotation is announced/predictable; an out-of-window key change is itself an incident signal |
| 10 | Token replay | A valid access token intercepted (e.g. via an insecure product-side log) and reused by an attacker | Short TTL bounds the exploitation window; HTTPS-only transport everywhere; `aud` scoping limits blast radius to one product | A token replayed within its TTL, against the SAME product's own API, from a different location, is not distinguishable from a legitimate mobile/roaming user without additional signal | Anomalous IP/geo/device patterns per `sub` (a product's own concern, not this platform's) | Short TTL (ADR-003, reaffirmed); `jti`-based introspection available for high-security callers (#22 in `docs/EXTERNAL_API_TRUST_BOUNDARY.md`) |
| 11 | Refresh-token replay | An already-rotated refresh token is presented again | Existing, unchanged mechanism: reuse detection revokes the entire session chain (Phase 1, reaffirmed for OAuth-issued refresh tokens) | None — this is already a hardened, tested mechanism | `security.suspicious_login`/reuse audit event (existing) | Unchanged — full session-chain revocation on detected reuse |
| 12 | Refresh-token theft | A refresh token exfiltrated from client storage (XSS against a SPA, insecure mobile storage) | Public clients should prefer a backend-for-frontend or secure, non-JS-accessible storage (HttpOnly cookie pattern) where the client architecture allows it — a client-side architecture decision this platform can recommend but not enforce; opaque refresh tokens (existing) are not self-describing, limiting value if exfiltrated without the ability to also call this platform's endpoints | A determined attacker with full client-side code execution (XSS) can use the token exactly as the legitimate client would, until rotation/reuse-detection catches the resulting fork | Reuse detection (#11) catches the FIRST fork the moment the legitimate client also tries to use its (now superseded) token | Rotation-with-reuse-detection (existing); short refresh-token TTL for non-"remember me" sessions (existing) |
| 13 | Audience confusion | A token issued for Product A presented to Product B's API, which fails to check `aud` | Mandatory, structural `aud` check (ADR-020 step 3) — called out as the single most important resource-server validation step | A resource server that skips this check entirely (an implementation defect outside this platform's direct control) | Cross-referencing which `aud` a token was issued for vs. which API logged accepting it (requires product-side logging) | Explicit, repeated documentation of this as non-optional (ADR-003, ADR-016, ADR-020, this document) |
| 14 | Issuer confusion | A resource server trusts tokens from an unintended issuer (e.g. a staging environment's `iss` accepted by a production resource server) | Per-environment distinct `iss` (`docs/KEY_MANAGEMENT_ARCHITECTURE.md` §6); mandatory `iss` check alongside `aud` | A resource server misconfigured to trust multiple issuers without justification | Any token from an unexpected `iss` at volume | Environment-separated signing keys make issuer confusion also a signature-verification failure, not just a claim-check failure |
| 15 | Scope escalation | A client attempts to use a token for an operation beyond its granted `scope` | Local scope-membership check on every request (ADR-020 step 6); scopes granted only from an Application's own `allowedScopes` allow-list at issuance | A resource server that doesn't actually check `scope` (implementation defect) | Requests attempting operations outside granted scope, if the resource server logs denials | Explicit ADR-020 pipeline step, non-optional |
| 16 | Tenant escalation | A caller attempts to access a tenant its Membership doesn't cover | Unchanged Phase 2C mechanism — Membership always re-derived and re-validated server-side, never trusted from a claim (`docs/ORGANIZATION_CONTEXT_SECURITY.md`) | None beyond what Phase 2C's own stabilization review already closed | Existing `organization_context.denied` audit event | Unchanged, reaffirmed |
| 17 | Organization escalation | A caller attempts to gain org-scoped grants for an organization outside its Membership | Unchanged Phase 2C mechanism (`UserRolesRepository.resolveGrants`) | Same as #16 | Same as #16 | Unchanged, reaffirmed |
| 18 | Cross-product token reuse | A token minted for TravelOS presented to Healthcare's API | Mandatory `aud` check (same control as #13, restated for the specific multi-product framing the brief calls out) | Same as #13 | Same as #13 | Same as #13 |
| 19 | Cross-tenant service access | A service with a valid credential attempts to act on a tenant it was never granted | `ServiceAccountTenantGrant` — explicit, durable, revocable per-tenant grant, checked on every request (ADR-015) | A misconfigured overly-broad grant (an operational/administrative error, not a protocol flaw) | Audit trail of every service-tenant grant creation/use, Platform-Operator-reviewable | Least-privilege grant issuance as a documented admin practice |
| 20 | Stale membership | A Membership revoked after a human token was issued continues to be honored | Live re-validation on every refresh (unchanged Phase 2C mechanism); `resolveGrants()`'s own live check for any permission-gated request | Bounded to the remaining life of an already-issued, not-yet-refreshed access token (short TTL) | `organization_context.cleared_stale` audit event (existing) | Unchanged, reaffirmed — this is exactly what Phase 2C's stabilization review already verified |
| 21 | Stale entitlement | A Tenant's Product Entitlement revoked after tokens were issued continues to be honored by a resource server that cached it | Product-owned caching policy — a short TTL is a product's own responsibility (ADR-020 step 10) | The product's own choice of cache TTL directly bounds this risk; the Identity Platform itself is always live/current when asked | N/A at the Identity Platform layer (its own `ProductAccessService` is never stale); product-side cache-hit-rate/staleness monitoring is the product's own concern | Recommend short TTLs in `docs/APPLICATION_AUTHORIZATION.md` guidance; live-check escape hatch always available |
| 22 | Service credential compromise | A leaked `client_secret` for a service-bearing Application | Hash-only storage; immediate, no-grace-period revocation available; blast radius bounded by `ServiceAccountTenantGrant` (ADR-015) — not every tenant the Product has ever entitled | Everything the compromised service's grants covered, until revoked | Anomalous client_credentials volume/origin, audit trail per grant | Immediate revocation + tenant-grant scoping limits blast radius even before revocation completes |
| 23 | Application credential compromise | A leaked confidential-client `client_secret` for a human-facing Application | Same as #22, plus: a compromised confidential client's tokens are still bound to individual human sessions/consent, further bounding what a stolen secret alone can do (it cannot mint tokens for arbitrary users without also compromising an authorization code or valid refresh token) | Same as #22, narrower (bounded by which users actually authenticate through the compromised client after compromise) | Same as #22 | Same as #22; `APPLICATION_DISABLED` as the emergency stop for the whole client |
| 24 | RLS bypass | An attempt to read/write across tenant boundaries at the database layer | Unchanged — `identity_app`/each product's own equivalent runtime role remains `NOBYPASSRLS`; RLS is defense-in-depth, never the primary authorization mechanism (ADR-020 §11, reaffirmed non-negotiable principle) | A misconfigured product's own database role granted bypass (outside this platform's direct control, but documented as a hard "never" in `docs/EXTERNAL_API_TRUST_BOUNDARY.md` §6) | Product's own DB audit/role-review practice | Reaffirm `NOBYPASSRLS` as a standing requirement for any product following this platform's isolation pattern |
| 25 | Platform Operator abuse | A Platform Operator grants itself/a service excessive tenant access, or attempts to use administrative capability as an impersonation path | Unchanged ADR-010 boundary — Platform Operator authority is administrative/configuration-only, never an identity-assumption mechanism; every grant action is itself audited (`scope='PLATFORM'`) | An operator with legitimate, over-broad administrative permissions (a personnel/process risk, not a protocol flaw) | Full audit trail of every `ServiceAccountTenantGrant`/`TenantProductEntitlement`/Application credential action, Platform-Operator-attributed | Grant-ceiling-style review process (mirroring the existing grant-ceiling rule for role assignment, ADR — `docs/AUTHORIZATION_ARCHITECTURE.md` §4) |
| 26 | Enumeration | Probing `/authorize`, `/token`, or organization-context endpoints to learn which clients/organizations/tenants exist | Identical, generic error responses for every denial cause (existing Phase 2C discipline, `docs/ORGANIZATION_CONTEXT_SECURITY.md` §3, extended to the OAuth surface by ADR-019); no distinguishing timing/response-shape signal | Sophisticated timing-side-channel analysis (a general, platform-wide residual risk already accepted in `docs/SECURITY_ARCHITECTURE.md`, not newly introduced here) | Elevated request-failure-rate monitoring per client/IP | Unchanged discipline, extended consistently to every new endpoint |
| 27 | Open redirect | `/authorize`'s `redirect_uri` used as a vector to redirect a user to an attacker-controlled page (with or without a valid code attached) | Exact, pre-registered redirect URI matching only — no runtime-supplied redirect target is ever honored if it doesn't exactly match a registered value (`docs/OAUTH_ARCHITECTURE.md` §4) | None if matching is implemented as exact string equality, not "starts with"/"contains" | Any `/authorize` request naming an unregistered `redirect_uri` is rejected and loggable | Reject at the earliest possible point (before any authentication step), never redirect to an unregistered URI under any circumstance |
| 28 | Token forwarding | A service receiving a human's access token simply relays it, unmodified, to a downstream service, which treats the forwarded token as though the original human were calling it directly | Prohibited as a supported pattern (ADR-021) — every service-to-service hop authenticates with its own credential; a human's identity travels only as inert request data, never a substituted bearer credential; mandatory `aud` validation (ADR-020) also structurally rejects a forwarded token audienced for a different service | An implementer who ignores this guidance and builds forwarding anyway (a code-review/implementation-discipline risk, not a protocol gap — the `aud` check still catches the naive case) | Any resource server logging acceptance of a token whose `aud` doesn't match its own identifier would already be a signature-verification-adjacent anomaly; server-side logging of unusual multi-hop call patterns | ADR-021's explicit prohibition + mandatory `aud` enforcement (defense in depth, not reliance on policy alone) |
| 29 | Confused deputy | Service B is tricked into using its own elevated authority on behalf of a request that did not legitimately originate from an authorized caller, because it trusted an artifact (a forwarded token, an unverified "on behalf of" claim) rather than independently authorizing the actual, current caller | Every hop independently authorizes its own, actual caller via the full ADR-020 pipeline — no privilege is inherited across hops merely because an earlier hop was authorized; impersonation and token forwarding are both prohibited (ADR-021), removing the two most direct paths to this class of confusion | A service with a genuine design/implementation defect that trusts caller-supplied identity claims without independent verification (an implementation risk this architecture guards against but cannot mechanically prevent in a product's own code) | Audit trails naming the actual authenticated principal at every hop make a confused-deputy chain reconstructable after the fact | Per-hop independent authorization (ADR-020) + prohibition of both impersonation and token forwarding (ADR-021) |
| 30 | ServiceAccount confusion (cross-application selection) | A caller authenticates as Application A (valid `client_id`/`client_secret`) but supplies a `service_account_id`/`service_account_secret` belonging to Application B, attempting to obtain a token `sub`'d to a ServiceAccount it does not actually control | `ClientCredentialsService` (Phase 2D.4) checks `serviceAccount.applicationId === application.id` as a hard, structural condition — a ServiceAccount lookup that succeeds but fails this check is denied identically to "ServiceAccount not found" (generic `access_denied`, never revealing that a same-named/id ServiceAccount exists under a different Application) | None — the check is a direct equality test on a foreign key, not a heuristic | A denial with `reasonCode: service_account_cross_application` in audit metadata (never surfaced to the caller) | Explicit ownership check, tested directly (`tests/phase2d4-client-credentials.e2e-spec.ts`, "cross-application ServiceAccount selection is denied") |
| 31 | Product authorization bypass via a non-product credential | A Platform Operator's own (legacy HS256) bearer token, or any credential from a structurally different trust boundary, is presented to a Resource Server route protected by `ResourceAuthorizationGuard`, attempting to reach a product's own authorization decision without a valid external principal at all | `ExternalBearerAuthGuard` (Phase 2D.5) rejects any non-RS256/wrong-audience token outright (401) before `ResourceAuthorizationGuard` ever runs — the two guards are structurally sequenced, never merged (`docs/RESOURCE_AUTHORIZATION_CONTRACT.md` §1); `ResourceAuthorizationGuard` itself additionally fails closed (401) if it is ever somehow reached without a principal already attached | None — the rejection happens at Layer 1, a purely structural/cryptographic check, not a policy decision that could be misconfigured product-by-product | A 401 with no distinguishing detail; internally logged as `missing_bearer`/`missing_principal` | Tested directly (`tests/phase2d6-resource-authorization.e2e-spec.ts`, "Platform Operator token cannot bypass product authorization") |
| 32 | Client-authentication downgrade at `/token` (authorization_code) | A CONFIDENTIAL client's `client_id` (not itself secret) is presented in the request body alone, omitting the `Authorization: Basic` header, attempting to redeem a code without ever proving possession of the client secret | `AuthorizationCodeGrantService` (Phase 2D.7) branches on header PRESENCE, not on caller-declared intent: a Basic header always means "authenticate as confidential" (`tokenEndpointAuthMethod === 'client_secret_basic'` required); its absence always means "authenticate as public" (`tokenEndpointAuthMethod === 'none'` required) — a CONFIDENTIAL Application (`'client_secret_basic'`) can never satisfy the second branch, so omitting the header is a hard `invalid_client`, never a silent downgrade | None — the check is a direct equality test on the Application's own immutable, server-derived `tokenEndpointAuthMethod` (ADR-018), not a heuristic | `invalid_client` (401) with `reasonCode: client_requires_authentication` in audit metadata (never surfaced to the caller) | Tested directly (`tests/phase2d7-authorization-code-pkce.e2e-spec.ts`, "a CONFIDENTIAL client cannot skip authentication by presenting only a body client_id") |
| 33 | Authorization-code / access-token confusion at a Resource Server | A Resource Server (or a naive client) treats an authorization code as though it were a bearer access token, presenting it directly to a protected API | Structurally impossible: an authorization code is an opaque, tenant-prefixed random value with no signature/claims of any kind — `ExternalAccessTokenValidator` requires a three-segment RS256 JWT with a recognized `kid`; a code presented as a bearer token fails `extractBearerToken`'s own JWT-shape pattern (or, if it happened to pass that shallow check, fails signature verification outright) | None — the two artifacts are structurally, not just conventionally, distinct (Invariant 1, `docs/OAUTH_AUTHORIZATION_CODE_PKCE.md`) | `invalid_token` (generic, same as any other malformed bearer) | Implicit in every `/token` denial test (a code is never JWT-shaped) plus the existing `bearer-token.util.spec.ts` JWT-shape rejection tests |
| 34 | ID Token accepted as a bearer Access Token | An OIDC ID Token (Phase 2D.8), a genuine RS256 JWT signed by this platform's own key, is presented to a Resource Server route (or `/userinfo`) as though it were an Access Token | `ExternalAccessTokenValidator` rejects any token carrying `token_use: 'id_token'` outright, checked FIRST, before any other claim is read — defense in depth on top of the ID Token's own structural lack of `tenant_id`/`jti` (which the validator independently requires) | None — the rejection is enforced by an explicit claim, not merely audience coincidence (verified even when the ID Token's OWN transaction also produced an Access Token audienced for the SAME resource) | `invalid_token`, reason `id_token_not_accepted` (never surfaced externally) | Tested directly (`tests/phase2d8-oidc-provider.e2e-spec.ts`, "an ID Token is REJECTED at the demo resource-server route") |
| 35 | Access Token accepted as an OIDC ID Token by a relying party | A client-side OIDC library naively accepts any RS256 token with the right `iss` as an ID Token, without checking `aud`/`token_use` | An Access Token's `aud` is the resource API, never the requesting client's own `clientId` — audience-based ID Token verification (RFC-conformant relying-party behavior) already fails; `token_use` is additionally absent/`'access_token'`, never `'id_token'` | A relying party that ignores both `aud` and `token_use` (an implementation defect outside this platform's control, same class of residual risk as #7) | N/A at the Identity Platform layer — this platform always signs a structurally distinguishable pair | Tested directly (`id-token.service.spec.ts`, `tests/phase2d8-oidc-provider.e2e-spec.ts` claim-shape assertions) |
| 36 | OIDC nonce omission/substitution/replay | A client's authorization request nonce is dropped, silently replaced by another value, or an attacker attempts to reuse a nonce from a different transaction | Nonce is mandatory whenever `openid` is requested (denied `invalid_request` before any code exists if absent); bound to the SAME authorization-code row PKCE/redirect_uri/client are already bound to — one code, one nonce, never regenerated or substituted at `/token` | None — the code's own row is the sole source of truth, atomically consumed exactly once (Phase 2D.7's own replay protection, unchanged) | `invalid_request` at `/authorize` (missing); structurally impossible to substitute at `/token` (no nonce parameter exists there) | Tested directly (`tests/phase2d8-oidc-provider.e2e-spec.ts`, "Nonce security" describe block, including cross-transaction non-contamination) |

## Phase 2D.4 implementation status (`docs/PHASE_2D4.md`)

`POST /oauth/token` (`client_credentials` only) makes the following rows above concretely exercised by live HTTP requests, each with its own passing e2e test: **#5** (client secret leakage — hash-only storage, verified via `verifyClientSecret`'s timing-safe comparison), **#6/#7** (JWT forgery / algorithm confusion — the issued token is independently verified via a live JWKS fetch + `jwt.verify()`, never merely decoded), **#13/#18** (audience confusion / cross-product reuse — `invalid_target` denial for any audience not in `Application.audiences`, wildcard values rejected), **#15** (scope escalation — `invalid_scope` denial for any requested scope outside `Application.allowedScopes`), **#19** (cross-tenant service access — the full deny-by-default `ServiceAccountTenantGrant` chain, including an immediate-revocation test), **#22** (service credential compromise — blast radius bounded by that same grant, demonstrated by the "Tenant A revoked / Tenant B unaffected" test), **#26** (enumeration — unknown `client_id` and wrong-secret both produce the byte-identical `invalid_client` response), **#30** (new, above). Not yet exercised by this phase: **#28/#29** (token forwarding/confused deputy — no resource server exists yet to receive and potentially misuse this token), **#8/#9** (JWKS/`kid` attacks — unchanged from Phase 2D.1's own coverage, not re-tested here), **#16/#17/#20/#21** (organization/membership/entitlement staleness for *human* tokens — not applicable to a service token, which carries neither claim).

## Phase 2D.5 implementation status (`docs/PHASE_2D5.md`, `docs/RESOURCE_SERVER_ARCHITECTURE.md`)

The Resource Server side of every threat above that is only meaningful once a *consumer* of the issued token exists is now concretely exercised: **#6/#7** (JWT forgery / algorithm confusion) — `ExternalAccessTokenValidator` rejects HS256, `alg=none`, and an attacker-keypair-signed token claiming the real `kid`, each with its own e2e test, now on the RECEIVING side (Phase 2D.4's own coverage was issuance-side only). **#8** (`kid` attacks) — `JwksClientService` never derives its fetch target from a token's own `iss`/`jku`, only a fixed operator-configured `OAUTH_JWKS_URI`; an unknown `kid` triggers a bounded, cooldown-protected refresh, never an unbounded one (new sub-threat, "JWKS refresh amplification," closed by construction and unit-tested directly — 4 dedicated tests). **#13/#18** (audience/cross-product) — a token forged for the wrong audience is rejected by the validator itself, independent of anything Phase 2D.4 already covers issuance-side. **#26** (enumeration) — every bearer/token failure collapses to the identical `invalid_token` response regardless of which specific check failed. **#28/#29** (token forwarding/confused deputy) — now has an actual consumer to reason about: `ExternalBearerAuthGuard` authenticates only the caller of the CURRENT request; this codebase introduces no mechanism for a service to forward its own incoming bearer token as a substitute credential for a downstream call, and no `on_behalf_of`/subject-override parameter exists anywhere in the new module — ADR-021's prohibition remains structurally unreopened, though a genuine multi-hop-service integration test is not built (no second real service exists in this codebase to hop to). New, resource-server-specific defenses added and tested: **tenant header spoofing** (`assertRequestedTenantMatches` — a caller-supplied `X-Tenant-Id` differing from the token's own `tenant_id` is denied, never silently substituted) and **request-context contamination** (`ExternalPrincipalClsStore`, verified directly under 16 concurrent requests across two distinct ServiceAccount/Tenant pairs with zero cross-contamination).

## Phase 2D.6 implementation status (`docs/PHASE_2D6.md`, `docs/RESOURCE_AUTHORIZATION_CONTRACT.md`)

**#25** (Platform Operator abuse) is now extended, and **#31** (new, above) added: a Platform Operator's own credential is proven, by a passing test, structurally incapable of reaching a product's own authorization decision at all — rejected at Layer 1 (`ExternalBearerAuthGuard`), never reaching `ResourceAuthorizationGuard`/any registered `ResourceAuthorizationPolicy`. **#28/#29** (token forwarding/confused deputy) gain a second layer of concrete enforcement: `ResourceAuthorizationPolicyRegistry`'s per-`productId` isolation is verified directly (a policy registered for one product is never invoked for a request naming another, even when both are registered simultaneously) — the authorization-layer analog of the audience-isolation guarantee Phase 2D.5 already proved at the authentication layer. **#15** (scope escalation) is extended with explicit AND/OR semantics (`requireScopes`/`requireAnyScope`) and a fuller exact-match test matrix (prefix/suffix/substring/case/duplicate/empty-scope collisions, all denied). A new class of risk this phase explicitly closes by construction: a registered product policy that throws, or returns an ambiguous/incomplete decision, is treated as a denial, never as success — tested directly, including confirming the thrown error's own message never reaches the caller.

## Phase 2D.7 implementation status (`docs/PHASE_2D7.md`, `docs/OAUTH_AUTHORIZATION_CODE_PKCE.md`)

The human-user counterpart to Phase 2D.4's machine flow makes the following rows above concretely exercised, now for a human, PKCE-bound, single-use artifact: **#1/#2** (authorization code theft/replay) — single-use enforced by an atomic conditional `UPDATE` (`AuthorizationCodesRepository.tryConsume`), verified directly under 16-way concurrent redemption of the identical code (exactly 1 success, 15 denials). **#3** (PKCE bypass) — `S256` mandatory for every client (public and confidential alike); `plain` and a missing challenge are both rejected at `/authorize`, before a code is ever issued; a wrong or malformed verifier is rejected at `/token`, generically, alongside every other invalid-grant reason. **#4/#27** (redirect URI manipulation / open redirect) — the exact-match `RedirectUriPolicy` (unchanged from Phase 2D.2) is now exercised by a real endpoint for the first time, with a dedicated test per attack shape (unregistered, prefix, suffix, query-mutated, entirely foreign origin) — every one of these is rejected as a **direct** response, never a redirect, closing the "attacker learns whether redirect_uri would have worked via a redirect it receives" sub-case outright. **#13/#18** (audience confusion) — the code's own bound audience is what the resulting token is signed for; audience is never re-requested or re-trusted at `/token`. **#26** (enumeration) — every `/token` denial for `grant_type=authorization_code` collapses to the identical `invalid_grant`, regardless of whether the code never existed, already expired, was already consumed, or was presented with the wrong client/redirect_uri/verifier. **#32/#33** (new, above). **#16/#17/#20** (tenant/organization/membership escalation and staleness) — now meaningfully applicable for the first time to an OAuth-issued (not just the legacy HS256) token: `AuthorizeService` independently revalidates the effective organization context live against the user's own current `Membership`, on every `/authorize` call, exactly mirroring the existing Phase 2C `refresh()`-time discipline — a stale or foreign organization selection is denied (`access_denied`), never silently downgraded or substituted. Not yet exercised by this phase: **#28/#29** (token forwarding/confused deputy) — no second real service exists in this codebase for a human-issued token to be forwarded to; **#8/#9** (JWKS/`kid` attacks) — unchanged from Phase 2D.1/2D.5's own coverage, not re-tested here (the human token is signed and verified through the identical `ExternalTokenService`/`JwksClientService` machinery).

## Phase 2D.8 implementation status (`docs/PHASE_2D8.md`, `docs/OIDC_PROVIDER.md`)

Adds **#34/#35/#36** (new, above), all tested directly. Also extends: **#6/#7** (JWT forgery/algorithm confusion) — the ID Token is signed and independently verifiable through the identical RS256/`kid`/JWKS machinery already proven for Access Tokens, now exercised by a dedicated unit suite (`id-token.service.spec.ts`) AND a live-JWKS-fetch e2e test (brief §58), never a second cryptographic implementation. **#13/#18** (audience confusion) — extended with the single most important new rule this phase introduces: an ID Token's `aud` is the OIDC client's own `clientId`, never a resource-API audience, verified by asserting the ID Token and Access Token issued in the SAME transaction carry DIFFERENT, non-interchangeable `aud` values. **#26** (enumeration) — extended to `/userinfo`: missing bearer, wrong audience, an ID Token presented as bearer, and a token lacking the `openid` scope are all rejected without revealing which specific condition failed beyond the standard `invalid_token`/`insufficient_scope` distinction RFC 6750 already requires. **#20** (stale membership/entitlement) is NOT re-exercised for OIDC claims specifically — `/userinfo` and ID-Token issuance both perform a fresh, live `SecurityUser` lookup (`findGlobalById`) on every call, so a user's current name/email/verification state is always reflected, never cached or stale by construction. Not yet exercised by this phase: **#28/#29** (token forwarding/confused deputy) — same reasoning as Phase 2D.7 (no second real service to forward to); the OIDC Client itself (the RP) is, by design, external to this codebase and not simulated here beyond the independent-verifier pattern brief §58 requires.

## Phase 2D.9 implementation status (`docs/PHASE_2D9.md`, `docs/OAUTH_OPERATIONAL_HARDENING.md`)

A new, orthogonal threat CLASS this phase addresses — availability/abuse
resistance and operational safety, not a new authentication/authorization
bypass. **New row**: **#37 Endpoint flooding/brute-force abuse** — a
single client/source repeatedly hammering `/authorize`, `/token`, or
`/userinfo` (credential-stuffing a ServiceAccount secret, PKCE-verifier
brute-forcing, or simple denial-of-service) | Rate limiting
(`RateLimitGuard`, keyed on `client_id` + hashed source, never bypassable
by varying an unrelated request field) | A distributed attack spreading
requests across many source identifiers (rate limiting is per-key, not
global — a genuine distributed-abuse mitigation, e.g. at a
reverse-proxy/WAF layer, remains an infrastructure-level control outside
this codebase) | 429 responses, `oauth_rate_limited` metric increments |
Tested directly (`tests/phase2d9-oauth-operational-hardening.e2e-spec.ts`,
"Rate limiting"). **Extends #26** (enumeration): rate-limit responses
verified to never distinguish a real from a fabricated `client_id`
(identical 429 body either way). **Extends every threat's own §7 audit
discipline**: `/userinfo` now records `OIDC_USERINFO_ACCESSED`/
`OIDC_USERINFO_DENIED` (previously unaudited, a Phase 2D.8 gap closed this
phase); every OAuth/OIDC audit event now additionally carries a
correlation id, verified never to itself leak a secret/token/code/nonce
and never to influence the underlying authorization decision.
