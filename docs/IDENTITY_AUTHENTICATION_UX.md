# Identity Authentication UX — End-User Surface

Phase 2UI.5. The operational reference for the tenant-scoped app's authentication journeys (`apps/web/src/app/` — login, password reset, invitation acceptance, organization selection, logout, session expiration) and the OAuth 2.1 Authorization Code + PKCE authorization shell (`apps/web/src/app/pages/oauth/`). Builds on `docs/IDENTITY_TENANT_CONSOLE.md` (Phase 2UI.4, the admin console this login flow leads into), `docs/OAUTH_AUTHORIZATION_CODE_PKCE.md` and `docs/OIDC_PROVIDER.md` (the backend contract this phase's OAuth shell calls, unmodified).

## 1. What already existed vs. what this phase built

Before this phase, the tenant app's authentication surface was substantially real, not placeholder: Login, Forgot/Reset Password, and Accept Invitation were all working, backend-integrated screens (Accept Invitation already had 6 tests; Login/Forgot/Reset had none). `AuthProvider` already implemented the full token-refresh/rotation lifecycle, in-memory Bearer-token storage, and organization-context switching. Confirmed absent: any post-login "choose an organization" screen, any dedicated session-expired UI (a toast only), and — the central finding of this phase — any frontend surface for `/oauth/authorize` at all; that endpoint existed purely as a backend API route with zero corresponding UI.

## 2. Login

`shared/auth/components/LoginForm.tsx` (new — extracted, unchanged in behavior, from the former `LoginPage.tsx`) is now the single login form, reused by both `LoginPage` (standalone `/login`) and `OAuthAuthorizePage`'s inline "please sign in" step. `LoginPage.tsx` is now a thin wrapper that owns only the post-login navigation decision (§4).

Verified, not rebuilt: email/password/tenant-code fields, password show/hide toggle, `autocomplete="username"`/`"current-password"`/`"organization"`, react-hook-form + zod validation, loading/disabled state during submit, keyboard-operable throughout. Error handling: every 401/403 from `POST /auth/login` already carries a safe, deliberately-generic-where-it-matters message from the backend (`AuthenticationService` collapses unknown-tenant/unknown-email/wrong-password into one "Invalid credentials" specifically to prevent account enumeration, while a locked or disabled account gets its own specific, safe, actionable message — both confirmed via direct backend read). `getAuthErrorMessage()` (new, `shared/auth/authErrorMessages.ts`, generalized from the former per-page `getLoginErrorMessage`) passes these through verbatim and substitutes a generic message only for network failures, 5xx, and rate-limiting (429) — never inventing a distinction the backend itself doesn't make.

**Account lockout vs. rate limiting** — both real, both distinct (confirmed by direct backend read): lockout is a per-account 403 after 5 consecutive wrong passwords for that specific user (`Account is locked due to too many failed login attempts`, 15-minute window); rate limiting is a per-IP 429 (`Too many attempts...`) protecting against broad abuse. The frontend's generic error passthrough already surfaces both correctly without needing to special-case either — the backend's own message already says which.

## 3. Reusable auth error system

`shared/auth/authErrorMessages.ts` (new) — `getAuthErrorMessage()` (brief §16's table, realized as: pass the backend's own safe message through for anything from `/auth/*`, substitute generic copy only for network/5xx/429) and `getOAuthErrorMessage()` (maps RFC 6749 `error` codes from `/oauth/authorize` — `invalid_request`, `unauthorized_client`, `access_denied`, `invalid_scope`, `invalid_target`, `unsupported_response_type`, `temporarily_unavailable` — to safe, non-technical UX copy; the codes themselves and the backend's `error_description` are never shown to the end user, since they're written for a developer integrating a client, not the person signing in).

## 4. Organization selection (brief §12 — the one genuinely new tenant-side journey)

Confirmed the backend never auto-selects an organization at login — every fresh session starts tenant-wide (`organizationContext: null`) regardless of how many organizations the caller belongs to; only an explicit `POST /auth/context/switch` establishes one. `LoginPage.tsx` now reads the freshly-established `{organizationContext, availableOrganizations}` returned directly from `AuthProvider.login()` (its return type was extended from `Promise<void>` to `Promise<LoginResult>` — the only AuthProvider signature change this phase made) and routes:

- Zero or one available organization with no ambiguity → straight to the original destination.
- Exactly one available organization → `/choose-organization` with `autoSelect: true`; that page calls `switchOrganization()` itself and continues without asking (nothing to actually choose between).
- More than one → `/choose-organization`, a real picker (`app/pages/ChooseOrganizationPage.tsx`, new) listing every organization the caller holds an ACTIVE membership in, plus a "Continue tenant-wide instead" option. Selecting one calls the existing, unmodified `switchOrganization()` — the backend independently re-validates the id against the caller's own memberships before anything changes; a denial is shown without losing the picker.

The routing decision deliberately reads `AuthProvider.login()`'s **return value**, not `useAuth()`'s context after the fact — React state updates aren't synchronously visible in the same closure, so relying on context here would have raced a stale render.

## 5. OAuth Authorization Shell — the central finding of this phase

`app/pages/oauth/OAuthAuthorizePage.tsx` (new) backs `GET /oauth/authorize` for a product-initiated Authorization Code + PKCE request (brief §5-8). Building this required first resolving a real architectural question, not assumed: **can a product's browser redirect to `/oauth/authorize` ever actually complete, given this platform's session model?**

Confirmed directly by reading `src/modules/authentication/guards/jwt-auth.guard.ts`: `JwtAuthGuard.readBearerToken()` reads `Authorization: Bearer <jwt>` **only** — there is no cookie fallback anywhere in this codebase. Confirmed directly by reading `src/modules/oauth/controllers/authorize.controller.ts`: `GET /oauth/authorize` is deliberately **not** `@Public()` — it runs behind this same `JwtAuthGuard`, by design (its own doc comment: *"the ONLY authentication mechanism this phase builds is 'already hold a valid platform session'... this endpoint never presents or implements a login form"*).

A genuine top-level browser navigation — the only way an OAuth redirect can land the user's visible tab on the product's own callback page — **cannot carry a custom `Authorization` header**; browsers only auto-attach cookies to navigations, never JS-held values. This means: **no real browser flow can currently complete `/oauth/authorize`'s success or denial redirect**, regardless of what UI is built in front of it. This is a genuine, pre-existing backend/session-architecture gap, not a missing frontend screen — and this phase's own brief explicitly forbids changing the V1 token architecture or introducing new protocol machinery (§19, §31) to close it (the standard real-world fix — a short-lived, purpose-built session cookie for exactly this hand-off — would itself be new token architecture). See §7 for the full, explicit gap entry.

### What the shell does, honestly, within that constraint

1. Parses `client_id`, `redirect_uri`, `response_type`, `scope`, `state`, `code_challenge`, `code_challenge_method`, `audience`, `organization_id`, `nonce` from the URL.
2. **Missing `client_id`/`redirect_uri` entirely** → a generic "Unable to process sign-in request" state, no backend call at all — this mirrors exactly what the real endpoint would itself reject as a direct 400, never a redirect (see `docs/OAUTH_AUTHORIZATION_CODE_PKCE.md` §4's own validation-order rule).
3. **Unauthenticated** → shows `LoginForm` inline, with a generic *"You're signing in to continue to an external application"* notice — the requesting application's name/branding is deliberately **never shown**, because no public, unauthenticated endpoint exists anywhere in this backend to resolve a `client_id` into a trusted display name (confirmed — every `applications` controller route is `PlatformJwtAuthGuard`-gated; a tenant-authenticated caller has no access to it either). Brief §8 is explicit that only a validated Application record may drive branding; since none is reachable, the honest choice is to show none at all rather than trust the unvalidated `client_id` query parameter. Documented as a real API gap (§7), not fabricated.
4. **Authenticated** → calls the real backend endpoint directly, with the caller's own Bearer token, using `fetch(..., { redirect: "manual" })` specifically so the two genuinely different outcomes can be told apart:
   - **A direct JSON response** (pre-`redirect_uri`-validation failure — unknown/inactive client, unregistered `redirect_uri`) — fully real and fully handled: mapped through `getOAuthErrorMessage()` and shown as safe text. This case is completely functional today.
   - **An opaque redirect** (`response.type === "opaqueredirect"` — every post-`redirect_uri`-validation outcome, success or denial) — the case this platform's session architecture cannot complete via any real browser navigation. Shown as an honest, dedicated "Unable to complete sign-in for this application" state (`EmptyState variant="not-available"`), never a doomed navigation attempt, never a fabricated success.

This design was arrived at only after directly verifying, in code, that no other technique (a `fetch()`-mediated redirect follow, `redirect: 'manual'` header inspection, or otherwise) can make the final hop both (a) genuinely complete the OAuth exchange and (b) land the user's visible browser tab on the product's own page — `fetch()` cannot produce a user-visible top-level navigation regardless of how its redirect handling is configured, and a raw top-level navigation cannot carry the required credential. See git history / this document's own drafting notes for the elimination process; the two email/description-only fixes considered (tokens in the query string; a new handoff cookie) are both explicitly prohibited by this phase's own brief.

## 6. Sessions and logout

Unchanged, verified correct: `AuthProvider.signOut()` calls the real `POST /auth/logout` (server-side session + refresh-token revocation, confirmed via backend read) then clears all local state and the entire React Query cache, best-effort even if the network call itself fails. **New this phase**: `SessionExpiredDialog` (`shared/auth/components/SessionExpiredDialog.tsx`) — a dedicated, non-dismissable-by-Escape modal replacing what was previously only a toast notification, shown by `AuthProvider`'s `onSessionExpired` listener. `AuthProvider` itself sits above the Router (see `App.tsx`) and so cannot call `useNavigate()`; the dialog's "Sign in" button only needs to close itself, since `ProtectedRoute` already redirects the page underneath reactively the instant `isAuthenticated` flips false.

## 8. Security-sensitive URL handling (brief §17)

Audited every query parameter this phase's own new code reads. `ProtectedRoute`'s existing post-login redirect (`state.from`) is **not** a URL/query-string mechanism at all — it's React Router's own `state` object, populated exclusively from an actual in-app navigation attempt, never parsed from `window.location.search` or any other attacker-influenced input; there is structurally nothing to validate because no string-based redirect target exists in that path. The OAuth shell's own query parameters (`redirect_uri`, `client_id`, etc.) are read but never independently trusted for navigation — the frontend never redirects anywhere itself based on them; the real destination is decided entirely server-side (either as a JSON error the frontend renders, or an opaque redirect the frontend explicitly does not and cannot follow — see §5). No open redirect exists anywhere in this phase's new code, by construction rather than by a defensive check.

## 9. Token handling (brief §19)

Unchanged (this phase made zero changes to token storage/refresh/rotation): access tokens remain JS-memory-only, refresh tokens in `sessionStorage`/`localStorage` per "remember me," never a cookie, exactly as `docs/IDENTITY_TENANT_CONSOLE.md` §3 already documented. `OAuthAuthorizePage`'s one raw `fetch()` call reads the current access token via `getSessionContext()` (an existing, already-exported accessor) purely to attach it as a `Bearer` header on that one request — the same mechanism `apiRequest()` already uses for every other authenticated call in this app, not a new token-handling path. No token is ever placed in a URL, logged, or sent to analytics by any code this phase added — verified directly in tests (`localStorage`/`sessionStorage` content assertions on `OAuthAuthorizePage.test.tsx`, `ForgotPasswordPage.test.tsx`, `ResetPasswordPage.test.tsx`).

## 10. Accessibility and responsive behavior

No new anti-patterns introduced (the one `autoFocus` added during development was caught by lint and removed, matching this project's established discipline). Every new screen (`ChooseOrganizationPage`, `OAuthAuthorizePage`, `SessionExpiredDialog`) reuses the same `AuthLayout`/`Card`/design-system components the pre-existing Login/Forgot/Reset/Accept-Invitation pages already use, inheriting their keyboard operability, focus management, and mobile-width behavior unchanged. `SessionExpiredDialog` is intentionally non-dismissable via Escape (verified by test) — a deliberate exception to typical modal behavior, since there is nothing left to "cancel" back into once the session has already been cleared.

## 11. What this phase deliberately did not touch

No MFA, Passkeys, SAML, Device Authorization, Token Exchange, Dynamic Client Registration, impersonation, or new grant types — none were implemented, none were even partially scaffolded. No change to the Platform Admin Console or Tenant Admin Console beyond the one genuinely shared component this phase needed (`LoginForm`, reused by both the standalone login page and the OAuth shell — no other console file was touched). No TravelOS, CTC Banking Intelligence AI, or QueueStream.health file, config, or dependency was touched. No new backend endpoint, DTO, or route was added — every gap in §7 is documented, not papered over.
