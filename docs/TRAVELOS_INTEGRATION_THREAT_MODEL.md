# TravelOS Integration Threat Model

Phase 2E.1. Integration-specific threats — additive to, never replacing, `docs/PHASE_2D_THREAT_MODEL.md` (Identity Platform's own frozen threat model, unchanged by this phase). Every threat is classified MITIGATED, ACCEPTED, or DEFERRED — none left unclassified, per the brief.

| # | Threat | Attack path | Control | Classification |
|---|---|---|---|---|
| T1 | Identity confusion | A TravelOS person with accounts in multiple tenants is reconciled to the WRONG global Identity Platform SecurityUser (e.g. two different people who happen to share an email typo-adjacent pattern get merged) | Reconciliation matches on EXACT email equality only (never fuzzy/similarity matching); every reconciliation row is individually reviewable/reversible (`travelos_user_identity_map`); CONFLICT status halts automatic merging when password hashes disagree (`docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §5) | MITIGATED |
| T2 | Tenant confusion | A TravelOS tenant's users end up associated with the WRONG Identity Platform Tenant | `travelos_tenant_identity_map` has a UNIQUE constraint on `travelos_tenant_id` — structurally one-to-one; every downstream reconciliation step (Organization, Membership) is FK-scoped through this one table, never independently re-derived | MITIGATED |
| T3 | Organization confusion | A Membership/role grant reconciled to the wrong Organization within a correctly-reconciled tenant | Organization reconciliation matches on `organizationCode` WITHIN the already-reconciled tenant only (`docs/TRAVELOS_IDENTITY_MAPPING.md` §3) — never cross-tenant matching | MITIGATED |
| T4 | User ID mapping attack | An attacker manipulates the migration process (or a race during it) to associate their own TravelOS identity with someone else's Identity Platform account | Reconciliation is an offline, operator-run, audited batch process against a read-only TravelOS snapshot — not a live, attacker-reachable API; no migration endpoint is exposed to end users | MITIGATED |
| T5 | Legacy token acceptance after cutover | TravelOS's resource-server continues accepting its own self-issued tokens for a tenant that has already been cut over (a stale flag, a caching bug) | Per-tenant cutover flag is the single source of truth for that tenant's accepted issuer; the migration plan explicitly prohibits "trust old tokens indefinitely" as a rollback strategy (`docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §6); Stage 3 removes the legacy validation code path entirely once every tenant is cut over, closing the risk permanently rather than leaving it dormant | MITIGATED (operationally — depends on TravelOS's own correct flag implementation in 2E.2+, not yet built) |
| T6 | ID Token used as API token | TravelOS's resource server naively accepts an OIDC ID Token as a bearer credential | Identity Platform's frozen `token_use` claim structurally prevents this (`docs/API_SECURITY_CONTRACT_FREEZE.md` §4) — but ONLY if TravelOS's own validator implementation actually checks it (`docs/TRAVELOS_INTEGRATION_ARCHITECTURE.md` §5 flags this as a required, not automatic, part of TravelOS's own implementation) | MITIGATED (by contract) / DEFERRED (implementation verification — 2E.7) |
| T7 | Wrong audience | A token issued for a different product (e.g. Healthcare) is accepted by TravelOS-Travel's API | Mandatory, per-product distinct audience (`docs/TRAVELOS_INTEGRATION_ARCHITECTURE.md` §7); TravelOS's own validator must reject any non-matching `aud` — same structural requirement as T6 | MITIGATED (by contract) / DEFERRED (implementation verification — 2E.7) |
| T8 | Wrong issuer | TravelOS's validator trusts a token from an unintended issuer (e.g. a staging Identity Platform instance's tokens accepted by a production TravelOS instance) | Mandatory `iss` check, one configured value per TravelOS environment, never multiple trusted issuers without explicit justification (mirrors `docs/PHASE_2D_THREAT_MODEL.md` #14, inherited) | MITIGATED (by contract) / DEFERRED (TravelOS environment configuration discipline — 2E.2) |
| T9 | Cross-tenant migration | A reconciliation error grants a person access to a tenant they never actually had a TravelOS account in | Membership rows are derived ONLY from actually-observed TravelOS `SecurityUserRole` data (`docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §1 Phase 6) — never inferred/assumed; RLS on `membership` (Identity Platform's own, unchanged, `docs/PRODUCTION_READINESS.md` §E) is defense-in-depth even if a reconciliation bug occurred | MITIGATED |
| T10 | Duplicate identity | Two Identity Platform SecurityUser rows are accidentally created for the same real person (reconciliation runs twice, or two different TravelOS tenants' rows fail to match) | `travelos_user_identity_map`'s PK (`travelos_tenant_id`, `travelos_user_id`) prevents re-processing the same source row twice; matching is exact-email, so a genuine cross-tenant duplicate is only missed if the email itself differs (a DIFFERENT, legitimate identity, not a defect) | MITIGATED (for idempotency) / ACCEPTED (a person using genuinely different emails per tenant will correctly NOT be merged — this is correct behavior, not a threat, but is recorded here since it could surprise an operator expecting automatic merging) |
| T11 | Membership escalation | Reconciliation grants a Membership with more access than the person actually had in TravelOS | Membership creation carries no role/permission data at all (Identity Platform's own Membership is access-context only, per the frozen contract) — TravelOS's own role/permission grants remain entirely TravelOS-side and unmodified by this migration (`docs/TRAVELOS_IDENTITY_MAPPING.md` §8) | MITIGATED |
| T12 | Role escalation | A TravelOS Group A permission (e.g. `TENANT_MANAGE`) is misread as authorizing Identity Platform platform-operator access | Explicitly and permanently NOT migrated — no code path maps a TravelOS role/permission into an Identity Platform platform-operator grant; Identity Platform's own platform-operator provisioning remains entirely separate, human-administered (`docs/PLATFORM_OPERATOR_ARCHITECTURE.md`, unchanged) | MITIGATED |
| T13 | ServiceAccount misuse | A future TravelOS backend-job ServiceAccount credential is used beyond its intended tenant/product scope | Unchanged Identity Platform invariant: `ServiceAccountTenantGrant` + `TenantProductEntitlement` both required (`docs/PRODUCT_INTEGRATION_CONTRACT.md` §6) — no TravelOS-specific exception is proposed | MITIGATED (by contract) / DEFERRED (no such ServiceAccount exists yet — inventory §17 UNKNOWN whether one is even needed) |
| T14 | Entitlement bypass | TravelOS's resource server allows a request without checking `TenantProductEntitlement` at all, assuming "TravelOS is the first/default product, so it doesn't need the check" | Explicitly rejected as a shortcut (`docs/PHASE_2D10.md`'s own brief language, "do not bypass entitlement because TravelOS is the first product," carried into this phase); the entitlement gate is enforced at Identity Platform's own token-issuance layer regardless of what TravelOS itself additionally checks | MITIGATED |
| T15 | JWKS trust misconfiguration | TravelOS is misconfigured to fetch JWKS from the wrong URL (e.g. a stale/attacker-controlled endpoint) | Same structural guidance Identity Platform's own `docs/RESOURCE_SERVER_ARCHITECTURE.md` §3 already gives every resource server: JWKS URI is a fixed, operator-configured value, never derived from token content; TravelOS's own deployment configuration is where this is set, requiring the same operational discipline TravelOS already applies to its OWN current `JWT_PUBLIC_KEY_BASE64` configuration | DEFERRED (TravelOS's own 2E.2 configuration correctness, not something this architecture phase can enforce in advance) |
| T16 | Dual-authentication bypass | During coexistence, a user exploits the SIMULTANEOUS existence of two valid login paths to gain access they'd be denied on one path (e.g. an account locked in TravelOS's own lockout logic still succeeds via Identity Platform because the lockout state was never reconciled) | A GENUINE GAP — TravelOS's `failedLoginCount`/`lockedUntil` state is TravelOS-local and NOT automatically synchronized to Identity Platform's own equivalent; a person locked out in TravelOS mid-coexistence could, if already reconciled with an Identity Platform account, still authenticate via Identity Platform normally, since Identity Platform's own lockout state is independent and was never triggered on that path | ACCEPTED — with an explicit, required mitigation for 2E.2+: coexistence-window operational runbook must include "check both systems" for any lockout/disable action during the coexistence window (the SAME class of process gap already flagged for "Revoked user" in `docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §3) — not silently accepted as fine, but not blocking this architecture phase either, since it is a process control, not a code defect requiring a design change |
| T17 | Rollback token abuse | An attacker exploits a "temporarily re-enable legacy token acceptance" rollback action to replay an old, otherwise-expired legacy token | Rollback re-enables ACCEPTANCE of TravelOS's OWN still-validly-signed tokens only — it does not resurrect an EXPIRED token (temporal validation is unaffected by the rollback flag) or accept a forged one (signature validation is unaffected); rollback is explicitly time-boxed and audited (`docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §6) | MITIGATED |
| T18 | Migration replay | The reconciliation batch process is run twice against the same TravelOS source data, attempting to re-create already-migrated rows | Map tables' PK/unique constraints make re-running the same phase a no-op for already-processed rows (idempotent by construction, `docs/TRAVELOS_IDENTITY_MIGRATION_PLAN.md` §1 Phase 3's own validation criterion) | MITIGATED |
| T19 | Partial migration inconsistency | A tenant's reconciliation is interrupted partway (e.g. Users done, Organizations not yet) and is queried/used in that inconsistent state | `migration_status` per row (`docs/TRAVELOS_IDENTITY_MAPPING.md` §4) makes partial state explicit and queryable; no tenant is cut over (Stage 2, `docs/TRAVELOS_AUTH_CUTOVER_PLAN.md` §1) until its ENTIRE reconciliation chain (Tenant → Organization → Membership → Entitlement) is complete, per the migration validation checklist | MITIGATED |
| T20 | Audit attribution mismatch | An identity-layer event that should now be attributed to Identity Platform's own audit trail is instead recorded (or double-recorded) against the wrong system, confusing incident investigation | Explicit event-type split (`docs/TRAVELOS_AUTH_CUTOVER_PLAN.md` §5) — LOGIN/LOGOUT/SESSION_* move to Identity Platform entirely post-cutover (not duplicated); business events stay TravelOS-only; correlation IDs (Identity Platform's own `traceId`/`correlationId` mechanism, `docs/OAUTH_OPERATIONAL_HARDENING.md`) are the intended cross-system correlation mechanism if an investigation ever needs to trace a TravelOS business event back to the identity-layer login that authorized it | MITIGATED (by design) / DEFERRED (an actual end-to-end correlation-ID propagation from TravelOS's own business-event logging back to Identity Platform's traceId is not yet built — TravelOS's own logging would need to forward it, a 2E.2+ implementation detail) |

## Summary

```text
MITIGATED: T1, T2, T3, T4, T7 (contract), T8 (contract), T9, T11, T12, T13 (contract), T14, T17, T18, T19
ACCEPTED:  T10 (correct-behavior edge case), T16 (process gap, documented mitigation)
DEFERRED:  T5 (operational — depends on 2E.2 implementation), T6 (implementation verification, 2E.7),
           T7/T8/T13 (implementation verification components, 2E.7), T15 (2E.2 configuration),
           T20 (correlation-ID propagation, 2E.2+)
```

No threat is left unclassified. Several are classified with BOTH a contract-level MITIGATED (Identity Platform's own frozen guarantee) and an implementation-level DEFERRED (TravelOS's own not-yet-built code must correctly apply that guarantee) — this dual classification is intentional: the ARCHITECTURE is sound, but its SECURITY depends on correct implementation in a future phase, which is exactly what `docs/TRAVELOS_AUTH_CUTOVER_PLAN.md` §6's security test plan (2E.7) exists to verify before production cutover.
